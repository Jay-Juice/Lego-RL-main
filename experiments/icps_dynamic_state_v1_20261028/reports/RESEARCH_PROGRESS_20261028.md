# 动态 PI 首轮研究记录

独立副本已建立，旧 ICPS 35 份源文件 SHA 均未变化。新副本继承的训练、模型、优化器和 SAO runtime 未改；继承的启动入口被禁用。当前实现是纯输入选择器及离线测试，**尚未接入正式在线代理，也没有开启训练**。

PI 上限保持 initial 192、update 128、episode 4096。初始候选保持原 issue-only top3；后续允许实际变化实体进入候选，并保留 issue 锚点。窗口引用当前真实源码，按已发可见内容去重，A→B→A 不能被全局 seen 吞掉，同逻辑请求不能重复扣预算。

## 同预算开发结果

607 个历史样本都已被观察过，全部是开发数据；其中 366 个可做精确改动行/锚点评分。标签由独立 scorer 读取，生成进程的 Landlock 拒绝标签文件访问，所有输出先冻结再评分。

| 方案 | 目标行/锚点可见 | 至少一个目标改动范围完整可见 |
|---|---:|---:|
| 原 ICPS v1.1 | 129/366（35.25%） | 53/366（14.48%） |
| R1 balanced / focused / flow | 111 / 106 / 120 | 52 / 42 / 60 |
| R2 compact | 130/366 | 56/366 |
| R2 diverse | 108/366 | 38/366 |
| R2 expand | 143/366（39.07%） | 88/366（24.04%） |

R1 把预算切成小语法片段，文件与函数可见性提高，但目标行覆盖下降；碎片与标记开销不能算有效信息密度改善。R2 保留原词法锚点的连续上下文，减少标记，并将剩余预算用于邻近源码。expand 比原版新增 16、丢失 2，开发集净增 3.83 个百分点；仓库聚类配对区间约 +1.06 至 +5.90 个百分点。该区间来自已用于迭代的数据，不能当作独立泛化证据。

R2 expand 的实际 token 中位数 190，原版 165；因此是同**上限**比较，不是每例实际 token 数完全一致。expand 独立编码的标记中位数 33 tokens、源码窗口中位数 16 行。这些成本统计不能直接推出每 token 的价值预测信息增加，后续还需比较真实动态重复率与有效覆盖。

## 为什么候选有 66%，窗口却没有

242/366（66.12%）表示候选实体范围与目标行/锚点相交。scorer-only 容量检查发现，这 242 例每例至少有一条目标行能放进 192 tokens。说明“目标行本身太长”不是这里的主要限制，选择与分配损失值得继续解决。

但是生成器没有真实目标位置。直接输出完整 top3 的字面成本中位数 1448.5 tokens，仅 6/242 能完整放进 192。该统计可能包含 class/method 重叠，不是最优压缩下界；它只说明不能把“至少一条目标行放得下”等同于“不知道位置也能全部覆盖”。Oracle 位置从未用于生成训练 PI。

expand 仍漏掉候选命中内 99 例：其中 16 例距最近可见窗口不超过 2 行、14 例为 3–5 行、11 例为 6–10 行、9 例为 11–20 行、42 例超过 20 行，7 例没有目标文件窗口。84/99 的目标行仍有 issue 词项重合，提示简单局部词法排序不能充分区分相关位置。下一轮需同时研究窗口边界和更远处的控制/数据依赖，不能只无限加大附近窗口。

## 动态验证及保留的失败

R1/R2 各 15 个本地字节 tokenizer 契约通过；R2 另 15 个真实 Qwen tokenizer 契约通过。这些均为 CPU，不是 GPU 或在线接入验收。

真实 W0 加构造新增文件事件的测试首次因源码已到 1500 文件容量而拒绝，原失败保留。第二次按 UID 排序预筛容量合格样本，不读取 outcome/位置；第 6 例在修改→回退时失败。诊断显示 issue 窗口的词法分数挤掉了实际变化窗口，导致可见内容相同，去重后回退输出为空；并非 episode 预算耗尽。

R3 修复只使实际变化窗口优先于未变化 issue 窗口；W0 的变化计数均为零，完整607复核仍为143/366与88/366。本地16项、真实Qwen tokenizer 16项契约通过。24个真实W0+构造新增/修改/回退场景全部通过：新增目标行可见old0/24、new24/24，noop/retry/rollback各24/24，最大update128 tokens。仅按源码容量排除1例后取UID排序前24，未按结果或标签选择。队列exit0；动态部分81秒。构造轨迹不等于真实Actor轨迹覆盖提升。

## 后续准入

R2 尚未达到事先记录的开发覆盖 +5 个百分点条件，不启动训练。可用性检查找到 3064 个未进入 607 开发集且排除 Verified500 的 exact-hunk 任务，其中 221 个来自 607 未见的 28 个仓库；尚未冻结或评分。需选定方法后做独立验证，再做在线 PI/因果/gather/预算集成、真实 Harbor 与八卡验收。
